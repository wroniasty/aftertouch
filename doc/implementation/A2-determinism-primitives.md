# A2 — Determinism primitives

The arithmetic layer every later part is written in: 16.16 fixed point with pinned
rounding, the angle model and its two lookup tables, the movement kernel that turns a
destination into a per-tick delta, the reference-shaped RNG, and the state hash that
makes "identical" a measurement rather than an opinion. It explicitly excludes the
entity structs and the arena (B1), the per-tick pipelines that *call* the kernel (B3
ball, B4 players), and the trace record format (A3) — A2 supplies the hash A3 diffs
on, not the record it lives in.

Depends on: A1   Blocks: A3, B1   Wave: 1

---

## 0. One-paragraph version

Everything in the match engine is one of four things: a fixed-point number, an angle,
a random draw, or a decision made from those. A2 builds those four and nothing else.
The work is small in volume and unusually high in consequence, because a rounding rule
chosen carelessly here is not a bug that shows up as a crash — it is a divergence that
appears at tick 900 in Wave 3 and cannot be traced back. Two findings from reading the
reference shaped the whole design. First, **both trig tables are exactly generatable**,
so no disassembly-derived table data has to enter this repo: the tangent table is
`round(32y/x)` verified against all 1024 entries, and although the mathematical sine
table differs from the reference's in 14 of 256 entries, the original consumes it as
`(v >> 8) * speed` and `v >> 8` is identical for all 256 — bit-exact for every input
the engine can present. Second, **the reference port's default build is deliberately
not faithful**: it computes `sin * speed >> 8` where the original computes
`(sin >> 8) * speed`, guarded by `#ifdef SWOS_TEST`, and comments that it is "more
precision". We implement the original, and A3's corpus must be recorded from a
`SWOS_TEST` build or every B part will be tuned against a wrong oracle. The part also
closes the decision that reaches furthest: **we build against the reference's Amiga
profile at 50 Hz** (§2.4a), so that a trace diff is an equality test rather than a
resampling argument.

## 1. Scope

**In:**

- `Fix` — 16.16 signed fixed point, with the reference's operation set, its three
  distinct integer conversions, and its deliberately asymmetric mixed comparisons.
- `Vec2`/`Vec3` over `Fix`, and the separate whole-unit destination type — positions
  are fixed-point, destinations are integers ([../STATE.md](../STATE.md) §2).
- The angle model: the two angle spaces, the octant quantiser, the `Dir` renumbering,
  and `kDefaultDestinations`.
- `kAngleTangent[32][32]` and `kSineCosineTable[256]`, generated by a committed script
  and committed as a generated header, with a verifier that diffs them against the
  reference when it is present.
- The movement kernel `CalculateDeltaXAndY`, including the domain reduction, both
  platform profiles, and the `AngleTo` wrapper for its angle-only callers.
- The RNG: table, two engine streams, the third stream B11 requires, seeding, and the
  discipline that keeps all of it inside state.
- `HashState` and the padding-free guarantee that makes it meaningful.
- The no-float / no-time / no-unseeded-randomness wall check, extending
  `tools/check_walls.py`.

**Out:**

| Excluded | Owner |
|---|---|
| Entity structs, the arena, the offset map | B1 |
| Ball friction, gravity, bounce constants | B3 |
| Speed tables, boundaries, the per-tick movement pipeline | B4 |
| The trace record format, emission, the viewer, the corpus | A3 |
| Golden-trace regression, CI wiring, the headless runner | A6 |
| Career-side fixed-point constants (the header is reused; the constants are not ours) | E1 |

A2 owns the *kernel*; B3 and B4 own every caller of it. The line is that A2 contains
nothing a match rule could change.

## 2. Design

### 2.1 Fixed point

`src/core/include/core/fixed.hpp` today is the [../PLAN.md](../PLAN.md) §5 sketch, and
its own comment says the rounding of `operator*` and `operator/` is a placeholder to be
pinned "when trace-diffing begins". This is that moment.

**The reference has no fixed×fixed multiply and no fixed÷fixed divide.**
`FixedPoint` ([FixedPoint.h](../../../reference/swos-port/src/util/FixedPoint.h))
offers `+`, `-`, unary `-`, `/(int)`, `>>=`, and mixed comparisons. That is the whole
type. Multiplication happens in the kernel, on raw `int`, as `trig * speed >> 8`.

So our `operator*` and `operator/(Fix)` are **inventions with no oracle**, and every
rounding rule we could pick for them is equally unjustified. They are removed. `Fix`
provides exactly the reference's operations plus what a call site actually demands,
and a new operation is added when a B part needs it and can say what the reference
does in its place. This is cheaper than it sounds: the engine multiplies by scalars
and shifts, and does so on raw integers by design.

**Three integer conversions, three names.** The reference distinguishes them and we
must too, because `ToInt()` reads like all three:

| Reference | Rule | Ours |
|---|---|---|
| `whole()` | `int16_t(raw >> 16)` — arithmetic shift, **floors**, and narrows to 16 bits | `Whole()` |
| `truncated()` | `whole() + (sgn() < 0 && fraction())` — toward zero | `Truncated()` |
| `rounded()` | `whole() + (fraction() > 0x8000)` — half-up, ties down | `Rounded()` |

`Whole()` is the one the engine uses for every gameplay comparison — it is the "high
word" read that [../BALL.md](../BALL.md) §1 describes. `ToInt()` is deleted rather than
aliased, so that no existing call site silently keeps a meaning it was never given.
The `int16_t` narrowing is kept: it is load-bearing at extreme coordinates and dropping
it is a silent behaviour change.

**Mixed comparisons are asymmetric on purpose.** From the reference:

```
a <  n   is   a.whole() <  n
a >  n   is   a.whole() >  n || (a.whole() == n && a.fraction())
a <= n   is   !(a > n)
a >= n   is   a.whole() >= n
```

`>` accounts for the fraction and `<` does not. Every dead-ball barrier and goal-frame
test in [../BALL.md](../BALL.md) §5–§6 goes through these, so the asymmetry is
gameplay, not sloppiness. It is transcribed with this table as its comment.

**Raw arithmetic goes through `uint32_t`.** Signed overflow is undefined behaviour;
MSVC and Clang are permitted to differ, and a determinism guarantee cannot rest on UB.
Every `Fix` operation computes in `uint32_t` and casts back, which is well-defined and
identical everywhere. Under a test build (`AT_FIXED_CHECKED`) the same operations
assert that no overflow occurred, so the release wrap is a documented fallback rather
than a silent one. Right-shift of a negative signed integer is well-defined arithmetic
shift in C++20, which we are on, so shifts need no such treatment.

### 2.2 The angle model

**There are two angle spaces and conflating them is the most likely silent error in
this part.** The reference kernel uses both, twelve lines apart:

| Space | Range | Zero | Sense | Used for |
|---|---|---|---|---|
| Table index (`angle`) | 0–255 | down | counter-clockwise | indexing `kSineCosineTable` |
| Game heading (`fullDirection`) | 0–255 | up | clockwise | everything else |

with `fullDirection = (256 - angle + 128) & 0xff`. They are given distinct types
(`TrigIndex`, `Heading`) so the conversion cannot be forgotten and a mix-up is a
compile error rather than a mirrored football match.

`Heading` is stored as `uint8_t` and allowed to wrap. Every consumer is modular — the
±16 pass cone and the `full + 128` flip ([../AI.md](../AI.md) §5.4, §5.7), the ±32
aftertouch rotation (§5.6), the octant quantiser — so wrapping is the correct semantics
and hand-written masking disappears. The kernel returns `int16_t` because it needs
`-1` for "no movement"; storage is `uint8_t`.

**The octant**, one implementation for five callers (ball
[../BALL.md](../BALL.md) §2, player [../MOVEMENT.md](../MOVEMENT.md) §3.4, CPU dribble
[../AI.md](../AI.md) §5.5, header trigger §5.7, aftertouch §5.9):

```
Octant OctantOf(Heading h) { return Octant((h + 16) & 0xFF) >> 5); }
```

**`Dir` is renumbered.** `src/core/include/core/match_input.hpp` currently declares
`Dir { None = 0, N, NE, E, SE, S, SW, W, NW }`. The reference numbering is `0` up,
`1` up-right, … `7` up-left, with `-1` for none
([../MOVEMENT.md](../MOVEMENT.md) §3.1). Every table in every reference document —
`kDefaultDestinations`, the `playerTurnFlags` bitmask
([../SETPIECES.md](../SETPIECES.md) §2), the aftertouch offset tables, the three-band
restart table ([../AI.md](../AI.md) §5.7) — is indexed by that numbering. Ours must
match it, with "none" carried as the same `-1` sentinel the reference holds in
`currentAllowedDirection`, not as a ninth enumerator. This is a breaking change to a
Wave 0 header and it costs nothing now and a great deal after B4.

`kDefaultDestinations[8]` — the ±1000 offsets of
[../MOVEMENT.md](../MOVEMENT.md) §3.2 — lives here rather than in B4, because it is a
direction primitive with five consumers across three parts.

### 2.3 The tables are generated, not transcribed

[../PLAN.md](../PLAN.md) §9 forbids the reference as a source of code. A 256-entry
trig table is data rather than code, but transcribing one is close enough to the line
to be worth avoiding if it is free. **It is free**, and that is a result rather than an
assumption:

**`kAngleTangent[32][32]`** is `round(32·y/x)` with the fold
`T[y][x] = 64 − T[x][y]` for `x < y`, `−1` at the origin, `0` along the top row and
`64` down the first column. Generated in pure integer arithmetic as `(64y + x) / 2x`,
it reproduces **all 1024 entries** of the reference table exactly. Verified.

**`kSineCosineTable[256]`** is nominally `round(32767·sin(2πi/256))`. The reference
table differs from that in **14 of 256 entries, always by ±1** (indices 25, 29, 93,
125, 163, 227, 231, 234, 238, 239, 241, 246, 248, 252). Transcription would seem to be
forced. It is not: the original consumes the table as `(v >> 8) * speed` (§2.4), and
`v >> 8` is **identical for all 256 entries** between the generated and reference
tables. The generated table is therefore bit-exact for every input the engine can
present, and the 14 deviations are unobservable.

They are *not* unobservable under the reference port's default `v * speed >> 8` path,
where 10 of the 14 change the result at some speed in 0–4096. That is one more reason
that path is not our oracle (§2.4).

Both tables are emitted by `tools/gen_trig.py` into
`src/core/include/core/trig_tables.hpp`, committed as generated source with the
generator named in its header comment. They are *not* generated during the build: a
clean clone must not need Python to be *correct*, only to have its walls checked.
`tools/verify_trig.py` re-derives both tables and diffs them against the reference
port when `../reference/` is present, including the `>> 8` equivalence argument above,
and is run by hand rather than by CI since the reference is not a checked-in dependency.

### 2.4 The movement kernel

`CalculateDeltaXAndY(speed, from, dest) -> {Fix dx, Fix dy, int16_t heading}` is the
whole of the engine's motion maths ([../MOVEMENT.md](../MOVEMENT.md) §1.2). Steps:

1. `dx = |dest.x − from.x|`, `dy = |dest.y − from.y|`, signs remembered.
2. `while (dx >= 32 || dy >= 32) { dx /= 2; dy /= 2; }` — reduce into the table's
   32×32 domain. Both values are already non-negative, so the division truncates
   consistently. **This is a deliberate precision loss on long vectors and must not be
   replaced by a full-precision `atan2`.** It is why a distant destination produces a
   coarser heading than a near one, which is visible in play.
3. `angle = kAngleTangent[dy][dx]`; `−1` means no movement and the kernel returns
   zero deltas and heading `−1`.
4. Fold the quadrant back to the full circle using the remembered signs, giving the
   table-index space; derive `fullDirection = (256 − angle + 128) & 0xff`.
5. `cos = kSineCosineTable[angle]`, `sin = kSineCosineTable[(angle + 64) & 0xff]`.
6. **`sin = (sin >> 8) * speed; cos = (cos >> 8) * speed;`** — see below.
7. PC profile only: `v − (v>>2) − (v>>4) − (v>>5) − (v>>6)`, the 41/64 frame-rate
   compensation, written as shifts because divisions round differently.
8. `deltaY.setRaw(sin); deltaX.setRaw(cos);`

**Step 6 is the finding that most affects other parts.** The reference port writes:

```cpp
#ifdef SWOS_TEST
    sin = (sin >> 8) * speed;      // "to comply with the original code"
#else
    sin = sin * speed >> 8;        // "by doing multiplication first ... more precision"
#endif
```

The port's **default build is knowingly not the original**. It is a better number and
a worse oracle. We implement the `SWOS_TEST` form, and A3 must record its corpus from
a **`SWOS_TEST` build running in Amiga mode** (§2.4a) — otherwise the corpus encodes
the port's improvement, every B part is tuned to match it, and the divergence number
that the whole of Wave 1 exists to produce is measuring the wrong thing. This belongs
in A3's subfile as a build requirement, not a footnote.

### 2.4a The platform profile — decided: Amiga, 50 Hz

Step 7 is `!amigaModeActive()` in the reference — an existing runtime switch, not
something we are inventing. `setAmigaModeEnabled()`
([amigaMode.cpp](../../../reference/swos-port/src/game/amigaMode.cpp)) is a thorough
one: the 41/64 factor, the four [../BALL.md](../BALL.md) §9 constants, the pitch
speed-influence table, the keeper dive deltas, nine timer intervals, and the
match-clock divisor (49 ticks per game-second against the PC's 70).

**We build against the Amiga profile at 50 Hz.** The reason is the instrument, not
nostalgia: at 50 Hz our tick *N* is the reference's tick *N*, so A3's trace diff is an
equality test. Against the DOS build at 70 fps there is no tick correspondence, and
"first divergence tick" — the acceptance criterion for every part from B1 to B10 —
would need a resampling convention that injects its own error into the one number the
project's whole method rests on. [../PLAN.md](../PLAN.md) §0 rule 3 already fixed the
tick at 50 Hz, which is the Amiga rate; choosing DOS would mean breaking that rule or
living with that seam forever.

What the choice costs, measured rather than asserted. **The 41/64 factor is not the
frame ratio** — 0.6406 against 50/70 = 0.7143 — so the DOS build is deliberately ~11 %
slower than the Amiga one rather than merely rate-adjusted:

| | DOS, 70 fps | Amiga, 50 Hz |
|---|---|---|
| Speed 0 | 80.6 u/s | 89.9 u/s (+11.5 %) |
| Speed 7 | 108.6 u/s | 121.1 u/s (+11.5 %) |
| Pitch length at Speed 7 | 5.90 s | 5.29 s |
| Air friction / gravity | 4 / 3291 | 10 / 4608 (2.5× / +40 %) |

The two builds therefore differ in **opposite directions at once**: Amiga is quicker
players and a heavier, deader ball; DOS is slower players and a floatier one. That is
the substance behind [../LEGACY.md](../LEGACY.md) §1's "they do not play the same",
and it is why this is a gameplay decision rather than a units conversion.

Two consequences to expect rather than diagnose later:

- **Raw tick counts stretch 40 % in real time.** `AI_resumePlayTimer`,
  `playerSwitchTimer`, `passKickTimer`, `wonTheBallTimer` and the 128-frame CPU jink
  period ([../AI.md](../AI.md) §5.5, §7) are uncompensated tick counts in both builds,
  so the CPU is slower in absolute time (jink period 1.83 s → 2.56 s). Genuine Amiga
  behaviour, but a feel change.
- **Stoppages run 27 % longer.** The interval table is ×10/11 in ticks, which is ×1.27
  in seconds (goal celebration 9.4 s → 12.0 s). The match clock is compensated, so
  90 minutes still takes 90 minutes.

**The honest caveat.** The port is a DOS disassembly with Amiga constants patched into
DOS code paths — the porters reconstructed Amiga mode, they did not disassemble the
Amiga binary. It is a legitimate 50 Hz oracle and it is not evidence of what the real
Amiga build did. "We build against the port's Amiga profile" is accurate; "we are
building the Amiga game" is not, and a divergence from a recording of real Amiga
hardware would not be a bug in our engine.

**The PC profile stays implemented** — four constants, one interval table and one shift
chain — so that B3 can A/B them once there is a match to feel, and so the decision
above is reversible by a one-line change rather than an archaeology exercise.
`PlatformProfile` is a compile-time constant carrying the 41/64 flag; A2 fills in the
trig half, B3 the physics half, B2 the timer intervals and clock divisor.

**`AngleTo(from, dest)`** wraps the kernel at the dummy speed of 256 used by
[../AI.md](../AI.md) §5.2 (`D5`) and [../MOVEMENT.md](../MOVEMENT.md) §3.4 (a player's
`fullDirection` toward the ball). Those call sites want an angle and not a motion, and
naming that intent stops `256` reading as a magic speed in three unrelated files.

### 2.5 The RNG

Structure from [../AI.md](../AI.md) §6 and
[random.cpp](../../../reference/swos-port/src/util/random.cpp): a fixed 256-byte
permutation, an 8-bit seed walking it, XORed with a key that is re-drawn only when the
seed wraps. Period 65 536.

```
uint8_t Draw() {
    if (seed == 0) xor_key = kRandomTable[++xor_index];
    return kRandomTable[seed++] ^ xor_key;
}
```

**A determinism trap in the reference, not to be inherited.** Stream 1's `xorKey` and
`xorIndex` are file-static globals outside the saved `swos` state, while stream 2's
(`randXorKey2`, `randXorIndex2`) live inside it. Restoring state therefore does not
restore stream 1, and a replay resumed from a snapshot diverges. **All three bytes of
every stream live in `MatchState`** for us. No global RNG, ever: a global is not
serialisable, not resumable and not diffable, and the trace harness needs all three.

**Three streams**, declared here even though only two have callers yet:

| Stream | Owner | Why separate |
|---|---|---|
| `gameplay` | the match engine | The one the trace hash covers |
| `presentation` | commentary, crowd, cosmetics | Must not perturb gameplay — the reference's `Rand2()` split |
| `resolve` | B11 result simulation | [PLAN.md](PLAN.md) §3 makes this non-negotiable: resolving other fixtures must not move the match stream. Free to declare now, expensive to retrofit. |

**Seeding.** The reference seed is 8 bits and the key/index another 16, so a 32-bit
engine seed cannot be poured in wholesale. The map is explicit rather than folded:
`seed = s & 0xFF; xor_index = (s >> 8) & 0xFF; xor_key = kRandomTable[xor_index];`
— 16 bits, which is the entire period. The upper 16 bits of the seed are **ignored,
not mixed**, and `Reset` documents that, because a seeding function that silently
discards entropy is worse than one that says so.

`kRandomTable` itself is the one artefact here with no formula behind it. See §6.1.

### 2.6 The state hash

`uint64_t HashState(const MatchState&)`, FNV-1a over the object representation.

The existing `static_assert(std::is_trivially_copyable_v<MatchState>)` in
`match_state.hpp` is not enough: trivially copyable permits padding, and padding bytes
are whatever the compiler left there. A hash over them is not a hash of the state, and
`memcmp` against a reference trace is not a comparison of the state. A2 replaces it
with

```cpp
static_assert(std::has_unique_object_representations_v<MatchState>);
```

which forbids padding outright. **This one assertion is what makes the A2 gate
meaningful**, and it is a constraint B1 inherits when it fills the struct out: field
order and explicit padding members become a design obligation rather than an
afterthought. It is far cheaper to accept now than to discover in Wave 2.

Note that the assertion **does not hold today**: `EntityState` is two `Vec3` (24
bytes) plus two `uint8_t`, which pads to 28. So work item 7 is not a one-line change
— it reshapes the struct the A1 skeleton shipped. That is the intended cost, and it
is why the item is scheduled rather than assumed.

### 2.7 The discipline

`tools/check_walls.py` today checks includes only. Rule 1 also forbids floats, clocks
and unseeded randomness, and [PLAN.md](PLAN.md) §7 lists "no float anywhere in
`src/core/`" as a wall check rather than a test. A2 adds the token scan over
`src/core`:

| Banned | Reason |
|---|---|
| `float`, `double`, `long double` | Rule 1; the reference's own `asFloat`/`fromFloat` are debug conveniences we do not need |
| `<cmath>`, `<random>`, `<chrono>`, `<ctime>` | The headers those arrive through |
| `rand(`, `srand(`, `time(`, `clock(`, `std::chrono` | Unseeded randomness and wall-clock time |

The scan strips comments and string literals first — enough to avoid the obvious false
positives without pretending to parse C++. A violation fails the default build, as the
include checks already do.

## 3. Interfaces

New under `src/core/include/core/`: `angle.hpp`, `trig_tables.hpp` (generated),
`trig.hpp` (the kernel), `rng.hpp`, `hash.hpp`, `profile.hpp`. Revised: `fixed.hpp`,
`match_input.hpp`, `match_state.hpp`.

What other parts see:

- **B1–B10** use `Fix` for every spatial quantity, whole `int16_t` for destinations,
  `Heading`/`Octant` for facing, and the three streams by name. They never index
  `kSineCosineTable` directly — the kernel is the only reader.
- **A3** consumes `HashState` and nothing else. The trace record is A3's design; A2
  gives it the number that makes two records comparable, and the `SWOS_TEST` build
  requirement from §2.4.
- **E1** reuses `fixed.hpp` for career arithmetic (the projection wall, [PLAN.md](PLAN.md)
  §3: "career arithmetic is fixed-point too") and shares no constants with the engine.

The wall: everything here is header-only or compiles into `at_core`, which keeps its
empty `target_link_libraries`. `trig_tables.hpp` is committed source, not a build step,
so a clean clone builds without Python.

## 5. Tests and acceptance

[PLAN.md](PLAN.md) §7 assigns A2: *golden vectors for fixed-point ops; property tests
over the arithmetic; cross-platform hash equality in CI.* All three, plus the table
verification that §2.3's argument depends on.

| Test | What it pins |
|---|---|
| `test_fixed.cpp` | Golden vectors per operation, **negatives and boundaries first**: `Whole(-1)`, `Whole` of `-0.5`, the three conversions disagreeing on the same value, each asymmetric comparison at `n`, `n ± 1/65536`. Property tests: `a + b − b == a`; `Whole` monotonic; `uint32_t` internals wrap identically to a reference model. |
| `test_angle.cpp` | Octant boundaries at every multiple of 16 (the `+16` bias is where an off-by-one hides); round-trip `TrigIndex ↔ Heading`; `Dir` values against the [../MOVEMENT.md](../MOVEMENT.md) §3.1 table by name. |
| `test_trig_tables.cpp` | All 1024 tangent entries against the integer formula; all 256 sine entries against `round(32767·sin)`; **and the `>> 8` equivalence claim of §2.3 restated as an assertion**, so that if anyone regenerates the table differently the argument fails loudly rather than silently. |
| `test_kernel.cpp` | Golden vectors for the eight axis and diagonal cases at several speeds; the domain reduction on a 1000-unit destination; heading `−1` when `dest == from`; isotropy of diagonals (`23170/32767`); **both profiles, with an explicit assertion that Amiga is the default** — a silent flip to PC would rescale every speed in the game by 0.64 and read as a tuning problem. |
| `test_rng.cpp` | Period is exactly 65 536; the wrap re-keys; the two streams are independent (draws from one do not move the other); `Reset` is idempotent; a golden first-64-draws vector per seed. |
| `test_hash.cpp` | Two default-constructed states hash equal; a one-bit change in any field changes the hash; the padding assert compiles. |
| `test_determinism.cpp` | **The gate.** A scripted input sequence over N ticks from a fixed seed, hashed, compared against a hash committed in the test source. |

**Golden data.** All of it is small enough to live in the test sources as literals
rather than as files — the largest is 64 RNG draws. It is regenerated by
`tools/record_golden.py`, which prints C++ literals to paste, so regeneration after a
deliberate rounding change is mechanical and reviewable in the diff.

**Invariants added to the always-on set** ([PLAN.md](PLAN.md) §7), asserted under a
test build from here on:

- No `Fix` operation overflows (`AT_FIXED_CHECKED`).
- `Heading` is always a valid `uint8_t`; `Octant` always 0–7.
- Every RNG draw comes from a stream that lives in state.
- `HashState` of a state round-tripped through its serialisation equals the original's.

**The demonstration that closes the part**: `test_determinism.cpp` passes on Windows
*and* on macOS against the same committed hash literal. That is the
[PLAN.md](PLAN.md) §3 "done when" in full — same seed and inputs, bit-identical state
hash on both platforms — and it is demonstrable before A6 exists, because a committed
expected value turns a cross-machine comparison into an ordinary test. A6 later wires
it into CI, which is where rule 5 is actually satisfied.

## 6. Open questions

**Closed while writing this part:** *which build is the oracle, DOS at 70 fps or Amiga
at 50 Hz.* Decided in favour of Amiga/50 Hz, with the reasoning and the measured cost
in §2.4a. It is recorded there rather than here because B3, B2 and A3 all need to read
it as a design constraint, not as an open item.

**6.1 — `kRandomTable`: transcribe, or use our own permutation?**
Unlike the trig tables, the 256-byte RNG permutation has no formula and cannot be
derived. Three options: transcribe it (exact reference behaviour, and the only way any
RNG-dependent trace diff means anything, but it is disassembly-derived data in the
repo); ship our own permutation (clean, and every RNG-dependent behaviour diverges
immediately, so the A3 corpus can only ever exercise deterministic scenarios); or
import it like an asset via A4, keeping ours as the committed default. **Resolved by:**
the same judgement that governs [../PLAN.md](../PLAN.md) §10 for artwork, and it should
be made by the same person on the same grounds. Note that it is *not* blocking: the RNG
structure, the stream discipline and every test above are unaffected by which 256 bytes
sit in the table.

**6.2 — Does the presentation stream belong in the hash?**
The reference's `Rand2()` split exists so cosmetics do not perturb gameplay. If the
presentation stream is in `MatchState` — and §2.5 says all streams are — it is in the
hash, so a commentary line drawn at a different moment reads as a divergence. Either
the hash covers a declared subset of state, or presentation draws move outside the
hashed region. **Resolved by:** A3, when it decides what a trace record contains; A2
should expose `HashState` as hashing an explicit field list rather than the whole
object so that the choice is available. Recorded here because deciding it in A3 without
noticing this is how a trace harness ends up reporting noise.

**6.3 — Where does the engine seed come from, and is it part of the trace?**
§2.5 consumes 16 bits of a 32-bit seed. Whether the seed is recorded in the trace
header, derived from the fixture, or supplied by the career layer is A3's and B11's
business, but a trace that does not carry its seed cannot be replayed.
**Resolved by:** A3's record format.
